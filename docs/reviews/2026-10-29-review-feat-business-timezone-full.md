## Minor

### 🟡 The new 409 `ONBOARDING_COMPLETE` contradicts spec 0008 AC-3, the API table, and the PR doc — `backend/src/presentation/controllers/business.controller.ts:338`

**Problem**: Commit `8b786d6` (landed after the last review) upgrades the draft endpoint to answer `409 { error: 'ONBOARDING_COMPLETE' }` when the repository skips the write. AC-3 of the governing spec says "No new endpoint, permission, error code, or audit row is added" (`docs/specs/0008-business-timezone/index.md:23`), the API surface table lists only "400, 401, 403" as key errors for `PUT /onboarding/draft` (line 61), and the PR doc written eight hours later still asserts "No new endpoint, error code, or permission" (`docs/PRs/2026-10-29-feat-business-timezone.md:11`). Only verify.md's new line 40 records the 409, citing the very AC that forbids it. The scope ledger does document the behavior ("a draft save that answers 409 once onboarding is complete"), so the sources disagree with each other.
**Why it matters**: The behavior change is correct engineering — a 200 for a write that never landed was dishonest, and five reviewers had asked for it. But the spec is the contract `/check verify` and future changes read; a hard-coded "no new error code" promise that is already false will mislead the next reader, and error-code changes are exactly what a consumer (a future API client) needs to know about. This is the same class of ledger honesty the previous review flagged as its one minor, now in the opposite direction: the code moved, the spec did not.
**Suggested fix**: Amend spec 0008 with a dated one-line update: AC-3's "no new error code" sentence gains "except `ONBOARDING_COMPLETE` (409) added on the draft route, see the Update", the API table row lists 409, and the PR doc's API bullet drops "error code" or names it. One edit each, no code change.

### 🟡 `BusinessResponseSchema` validates the draft's timezone while deliberately not validating the stored one, against its own rule — `packages/contracts/src/business.ts:132`

**Problem**: The schema's `data.timezone` is presence-only (`z.string()`), justified by AC-2/AC-11 and the test comment "a corrupt stored value must still read", and the contracts AGENTS.md sentence synced in this very branch states the rule generally: "A response schema that must read a legacy or corrupt value checks presence only, so a bad stored value cannot fail a read." The new `onboardingDraft` field uses `TimezoneSchema.optional()` inside the same response schema, and a test pins the rejecting behavior (a draft with `Mars/Olympus` fails the parse, `packages/contracts/src/business.test.ts:61-67`). So one stored timezone in one response must survive corruption and its twin must not.
**Why it matters**: Impact today is zero — no application code calls `.parse` on a business response (only contracts tests do), and the frontend handles a corrupt draft zone with its own `safeParse` fallback (`frontend/src/app/onboarding/page.tsx:179-180`). But `BusinessResponseSchema` exists precisely so some future consumer can validate the payload the API actually sends, and the API does return drafts whose stored JSONB could predate a policy change or be edited outside the app; a strict consumer would then fail the whole read of a profile whose top-level timezone the schema deliberately tolerates.
**Suggested fix**: Either make the draft's timezone presence-only like its sibling (`z.string().optional()`), or document in `OnboardingDraftSchema` why the draft is stricter (it can only ever be written through `DraftSaveSchema`, never by legacy code) — one of the two, so the rule in the contracts AGENTS.md and the schema agree.
