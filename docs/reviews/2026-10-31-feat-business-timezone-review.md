## Minor

### 🟡 `BusinessResponseSchema` rejects the `logoUrl: ""` that this branch's own onboarding flow produces — `packages/contracts/src/business.ts:130`

**Problem**: The completion request sends `logoUrl: form.logoUrl`, which defaults to `""` when no logo was uploaded (`frontend/src/app/onboarding/page.tsx:308`). `BusinessProfileSchema.logoUrl` accepts `""` (`or(z.literal(''))`), the repository stores it, and `GET /me` then returns `logoUrl: ""` (`backend/src/presentation/controllers/business.controller.ts:120`). But `BusinessResponseSchema.logoUrl` is `z.string().url().nullable()` — it accepts a URL or `null`, not the empty string the API now returns for every business completed without a logo. The two schemas were inconsistent before this branch too, but the path that manufactures the `""` (completion, with the write schema's `or(z.literal(''))`) is this branch's centerpiece flow, and the same file was edited on both sides without the read side catching up (the sibling draft-timezone strictness was fixed in exactly this way last pass).

**Why it matters**: No application code parses a response with `BusinessResponseSchema` today, so nothing breaks now — but the schema exists precisely so a future consumer can trust the payload the API sends, and its inferred `BusinessResponse` type already misreports (`logoUrl: string | null` while `""`, `null`, and a URL are all live values). The first consumer to validate against it fails the profile read for every logo-less business.

**Suggested fix**: Make the response schema accept what the API returns: either widen it (`z.string().url().nullable().or(z.literal(''))`) or normalize at the entity/controller level so a cleared logo reads as `null`, and pin both shapes (cleared and set) in `business.test.ts`. The controller returning `logoUrl: business.logoUrl || null` is the smaller diff and also removes the double falsiness handling in the screens.

**Resolved 2026-10-31**: took the normalization route at the repository, the one place every read passes through, so the response contract stays strict (a URL or `null`, never `''`). `toBusiness` in `backend/src/infrastructure/drizzle/repositories/business.repository.ts` maps a stored `''` to `undefined`, and `updateProfile` writes `''` as `null`, so the column holds one shape. The sign in payload in `backend/src/infrastructure/database/drizzle/repositories/auth.repository.ts` now answers `null` too. The `Business` entity documents the rule. Pinned by `business.repository.integration.test.ts` (an empty logo round trips to `undefined` and the column holds `null`; a row already stored as `''` reads as `undefined`), both verified red without the fix, and by `packages/contracts/src/business.test.ts` (accepts `null` and a URL, rejects `''`). Suites after the fix: contracts 113, backend 390, frontend 301; e2e 42 of 42 on desktop and mobile; typecheck, lint and format clean.
