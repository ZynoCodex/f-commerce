## Minor

### 🟡 Initial list loading is rendered with unannounced skeletons, contradicting AC-14 — `frontend/src/app/orders/page.tsx:334-340`

**Problem**: AC-14 requires "Empty, no match, loading, and error states are present and announced" on `/orders`. The initial load renders three `<Skeleton>` divs with no live region, `role`, or text, so a screen reader hears nothing until rows arrive. The neighbouring states do this correctly: the load-more loading state uses `role="status"` (`:342-346`) and errors use the `ErrorState`/`role="alert"` path (`:348`). The same gap applies to the `EmptyState` swap, which is likewise not a live region. Two prior reviews recorded this at nit level and `docs/specs/0007-orders/verify.md:92` self-acknowledges it, but it is an explicit, independently checkable AC contradiction rather than a stylistic preference, so this review rates it Minor.

**Why it matters**: The project targets WCAG AA and is the stated acceptance contract for this screen; a new seller session opening `/orders` on a slow link gets a silent page for however long the 20-row query takes.

**Suggested fix**: Render the initial loading state the same way the load-more state is rendered — a `role="status"` region with `Loading orders…` text alongside (or instead of) the skeletons — and give the empty state container a `role="status"` so the swap is announced. Update the `verify.md` note when done.

## Strengths

- The verification test that closes the prior finding is the real thing: it imports the production `OrderUpdateSchema` from the contracts barrel, parses a 201-row edit payload end to end, and asserts both the failure and the `items` issue path — a boundary assertion on the live schema, not a mock stub or a copy of the create case.
- Test quality stands out at the integration level: the route suite drives real HTTP against the real database and asserts persisted rows directly (counter values, history rows, audit rows), covers the spec's ACs 1–19 including the two concurrent-create race, the same-key idempotency race (one 200/one 201, exactly one stored row), rollback on a forced audit failure (counter, order, lines, history, and audit all absent), and repository-level line scoping so an UPDATE can never rewrite another order's line.
- The concurrency core is structurally sound: the version guard sits in the `WHERE` of every write, the counter is serialized by the `business_order_counters` upsert with `orders_business_order_number_unq` (present since `0000_init`) as the database backstop, and the error precedence (existence → lock → transition → version) is enforced and asserted.
- The delivery-deadline slice is careful about its own edge: string-mode date column, hand-split rendering that never constructs a `Date`, viewer-local `localToday()` for the badge, blank-to-null parsing before validation, and a new component test (`order-deadline.test.tsx`, untracked) plus unit, route, and E2E layers that pin the badge rules across statuses.
