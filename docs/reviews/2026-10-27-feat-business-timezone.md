## Summary

The change stores one not null `businesses.timezone` column (one generated migration, `Asia/Dhaka` default), validates every write through a shared `TimezoneSchema` that canonicalizes lowercase IDs and IANA aliases, maps the field through entity, service, repository, and all four business endpoints, and then uses the stored zone on every surface the spec names: the settings and onboarding grouped select with its confirmation dialog, the shell badge and header day, every console timestamp, the delivery date warning, and the derived Overdue badge. A client `BusinessSettingsProvider` with `useSyncExternalStore`, a versioned per business `localStorage` cache, and a new auth subscription replaces the per page currency fetches. Independent of the prior review, I traced the fetch and set pipelines, the draft race guard, the DST and leap day helper, and the AC-5, AC-6, and AC-12 flows. The implementation matches spec 0008 line for line and the test depth is genuinely strong. What remains open are the same three deferred minors the author consciously recorded as follow ups in `nextTask.txt` (always guarded setter, hot path formatter cost, payments prep), plus one redundant fetch inefficiency the previous pass did not name.

## Minor

### 🟡 `updateSettings` commits under whatever auth is active at write time, no landing guard, `frontend/src/components/business/business-settings-provider.tsx:212-217`

**Problem**: The provider's fetch path defends against a sign out or business switch while its request is in flight (lines 191-194 drop the commit when the active business no longer matches). The setter path has no such guard: `updateSettings` reads `getAuth()` at handler time and writes the incoming (possibly stale) settings into whichever business is active then, including that business's cache.
**Why it matters**: Unreachable through today's UI (login reloads, sign out nulls `getAuth`, there is no switcher), but it is the exact cross tenant `localStorage` leak the fetch path already guards against, and it becomes live the moment a business switcher or multi membership STAFF flow lands. `backend/src/infrastructure/database/drizzle/repositories/business.repository.ts:59-86` shows the team already knows this race class: the new `onboardingComplete = false` filter closes its own version of it for writes already in flight.
**Suggested fix**: Capture the business id the save belongs to alongside the settings and drop the commit inside `updateSettings` when `getAuth()?.businessId` no longer matches, one guard mirroring the fetch path. The author's `nextTask.txt` defers this to the switcher slice. If that deferral stands, the two follow up lines proposed there must actually be written into `docs/specs/0008-business-timezone/index.md` (see nits) so the deferred guard survives the merge.

### 🟡 Timezone validation runs repeatedly on the render hot path, `frontend/src/lib/timezone.ts:6-8`, `frontend/src/components/business/business-settings-provider.tsx:76-105`, `frontend/src/lib/catalog-format.ts:17-27`

**Problem**: The frontend `isValidTimeZone` delegates to `TimezoneSchema.safeParse`, which resolves the zone once in `refine` and again in `transform` (`packages/contracts/src/business.ts:33-39`), so two `Intl.DateTimeFormat` constructions per call. That cost lands in more places than the previous review noted. `getSnapshot` (`business-settings-provider.tsx:76-105`) calls it on every render of every consumer, because validating from the cache inside `computeSnapshot` runs on each render pass: it does `getAuth()`, one `localStorage` read plus `JSON.parse`, and two Intl constructions just to return a value whose key has not changed. On top of that, `todayInTimeZone`, `formatBusinessDayLabel`, and `formatDateTime` each validate once more before building their own formatter, and the orders list calls `formatDateTime` twice per row (table cell plus phone card).
**Why it matters**: Not a correctness issue at 20 rows per page, but this is work inside the render path that belongs outside it, and it multiplies with list size. The backend helper (`backend/src/domain/timezone.ts:14-27`) already demonstrates the cheap shape: one regex, one construction.
**Suggested fix**: Implement the frontend `isValidTimeZone` with the shared regex plus a single `Intl.DateTimeFormat` construction (mirroring the backend), trim the double resolve in `TimezoneSchema`, and key a small formatter `Map` by zone or at minimum cache the validated zone inside `getSnapshot`'s snapshot key so a revisit with unchanged values does not re-parse. The author's stated plan (own commit, spy based guard test in `nextTask.txt`) is reasonable. It just must not evaporate with the branch.

### 🟡 Redundant profile fetch fires on every auth change while already authed, `frontend/src/components/business/business-settings-provider.tsx:174-210`

**Problem**: The effect both runs its own `load()` and subscribes `load` to auth changes. On `setAuth` with a new business id, the old effect's subscription fires `load()` (a first `GET /api/business/me` targeted at the new business, because `getAuth()` is re-read inside `load`), then React re-renders, the effect re-runs, and fires the request again, so two identical fetches per business switch or login into a different business. Plain first login is one fetch, and both responses in flight are commit guarded, so this is benign duplication. The double load is also what makes it hard to see whether the AC-7 "loads once per auth change" contract holds by reading the code.
**Why it matters**: Small waste on a rare path, but it is exactly the kind of duplicated cause and effect that bites when a switcher is added and loads start racing with different tokens.
**Suggested fix**: Drop `subscribeToAuth(load)` from the effect. The `[businessId]` dependency plus `subscribeToAuthChanges` in `subscribeToSettings` already cover both the business change (effect re-run) and the token only change (re-render when the auth wrapper listener fires; the token only case needs either the subscription or a render signal, so pick one mechanism rather than both that overlap). Or subscribe to token changes only. Cover it with a test asserting `fetch` call counts on `setAuth`.

### 🟡 Unrelated `PaymentMethod` widening rides in this timezone branch, `backend/src/domain/entities/financial.entity.ts:3-11`

**Problem**: `CASH_ON_DELIVERY`, `CARD`, and `PAYPAL` are added to the enum that only types the `payments.method` text column (`schema.ts:389`). No consumer, no check constraint, no error path in this slice. I verified nothing in contracts, backend, or frontend reads the new values. It is clearly documented as feature 10 prep (`chore(payments)` commit plus the `docs/scope/scope.md` payments row), but it still lives in the timezone branch's revert range and diff narrative.
**Why it matters**: History hygiene. A payments reviewer sees a three line enum change out of context, and if feature 10 later re-types the column or adds a `Record<PaymentMethod, ...>` map, this branch is where the widening landed without review of those consequences.
**Suggested fix**: Per the author's recorded decision, keep it here but name it in the PR or merge description as feature 10 prep ("payments method set from scope feature 10") so the eventual payments review finds it knowingly. If the branch is rebased before merge anyway, move it to the payments branch instead.

## Nits

A single `transform` that reports failure (`z.custom` style) would canonicalize once. The backend `isValidTimeZone` shows the single construction shape.
- ⚪ `backend/drizzle/migrations/0006_absurd_hobgoblin.sql:1` and `backend/drizzle/migrations/meta/_journal.json` lack a trailing newline. Harmless, but it re-diffs every regeneration.
- ⚪ `frontend/src/lib/timezone.ts:15,32`, the zone is used untrimmed after validation while the backend helper trims it (`backend/src/domain/timezone.ts:36`, `timezone.ts:31-33` there). Harmless because provider values are always canonical, just a consistency split between the two copies.
- ⚪ `frontend/src/app/onboarding/page.tsx:133-134` (and `settings/page.tsx`), `void cancelled;` is a dead statement implying a purpose it does not serve. Drop it.
- ⚪ `frontend/src/app/customers/[id]/page.tsx:54-57`, this page keeps its own `formatMoney` (`style: 'currency'`) while every other touched surface uses the shared plain number plus code formatter. Pre existing scope made visible by this slice, fold into a future currency polish pass.
- ⚪ `nextTask.txt` records the decision to write two follow up lines (business switch guard on `updateSettings`; single construction and helpers reuse) into `docs/specs/0008-business-timezone/index.md`, but the spec's Follow-up section does not contain them (`index.md:164-171`). ## Strengths

- The stale draft race is closed with defense in depth and a real reproduction: the wizard clears its pending debounce before completing (`onboarding/page.tsx:259-263`), and the repository's `WHERE ... AND onboarding_complete = false` filters away a draft write already in flight, with a genuine Postgres integration test driving the exact interleaving (`business.repository.integration.test.ts:161-172`). This is beyond what the spec asked and it is correctly reasoned in the code comment.
- The provider gets the hard `useSyncExternalStore` details right: module level snapshot caching keyed on value equality so `getSnapshot` stays referentially stable, server and hydration renders pinned to the fallback via `getServerSnapshot`, per business cache isolation with malformed entries removed, and a race guard on the fetch in flight. The 13 provider tests are sensitive to mutation (each asserts the snapshot and the persisted file), not smoke tests.
- Validation is designed as a contract, not a UI habit: one `TimezoneSchema` is the single source of truth for the onboarding completion, the profile update, the draft branch, the cache read, and the provider write path (`sanitizeSettings`), and the tests cover the honest hard cases: `asia/dhaka` canonicalization, the runtime dependent `Asia/Calcutta` alias, offsets and abbreviations rejected, and a runtime independent DST and leap day table for the day helper on both copies (backend `timezone.test.ts:30-63`, frontend `timezone.test.ts:20-45`).
