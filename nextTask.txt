Q: The refresh cookie, only if you go cross-domain
If you ever host the frontend and API on different registrable domains (not app.example.com + api.example.com, which are same-site — but e.g. x.vercel.app + y.onrender.com), sameSite: 'strict' means the browser never sends the refresh cookie. That path needs sameSite: 'none' + secure + real CSRF protection. Staying same-origin avoids all of it. Flagging it because "deploy anywhere" often quietly means "deploy them to two different domains."

Short answer: not necessary for your setup, and nothing in the cookie needed a behavior fix. The warning is real only when the browser calls the API host directly. In this app it never does: client code calls relative /api/* paths on the frontend origin, and the Next.js server on the frontend host proxies them to the backend server to server. SameSite is a browser rule, and server to server hops are invisible to it.
Concretely, with frontend on x.vercel.app and backend on y.onrender.com:
1. The browser loads and calls only x.vercel.app.
2. Login responds with Set-Cookie: refreshToken=...; Path=/; HttpOnly; SameSite=Strict and no Domain attribute, so the browser stores it for x.vercel.app (host only).
3. A later /api/auth/refresh goes to x.vercel.app with the cookie attached. It is first party, Strict is satisfied, the Next proxy forwards it to y.onrender.com, and the rotated cookie comes back the same way.
I proved the exact two service shape locally just now, split like yours. Register through the frontend origin returned the Set-Cookie above, refresh through the same origin returned 200 with a rotated cookie, and the same call without the cookie returned a clean 400. The only production differences are the HTTPS hop and the Secure attribute (set when NODE_ENV=production), both handled by the browser as first party. The two different domains are fine; what matters is the browser's view, which stays one origin.
When it would bite you (the tripwire worth remembering): the moment any browser code calls the API host directly, for example an absolute https://y.onrender.com/api/... in a component or a public API URL variable. Then the fetch is cross-site (vercel.app and onrender.com are different sites, and separate *.vercel.app subdomains never count as one site either), Strict means the browser will not attach the cookie, and session refresh silently stops while login still appears to work. That path needs SameSite=None + Secure + a real CSRF defense. Keep client calls relative and this never happens.
What I changed anyway, because a review finding should end up recorded, not just answered:
- backend/src/presentation/controllers/auth.controller.ts: the four copied cookie option blocks are now one setRefreshCookie helper with a comment stating why SameSite=Strict is load bearing and what the cross-domain path would require.
- docs/specs/0001-stack-and-architecture.md: fixed a sentence that claimed cookie endpoints have "an explicit CSRF defense" (they do not; SameSite=Strict is the defense), and the deployment contract now records the single-origin constraint.
- Root AGENTS.md: one clause on the deployment bullet so future code keeps client calls relative.
- The cookie itself is untouched: Strict, host only, Secure in production. That is correct for this architecture, so there was nothing behavioral to fix.
- Verified after the change: backend typecheck and lint clean, format:check clean, and the 26 auth controller tests pass.
For the live test, the thing that actually breaks people:
1. API_ORIGIN on the frontend host must be set at build time (it is read in next.config.ts during next build). Setting it only as a runtime variable on Vercel changes nothing, and changing it needs a redeploy. If /api/* fails, it is almost always this.
2. Set NODE_ENV=production on the backend so the cookie gets Secure.
3. CORS_ORIGINS does not matter for the proxied flow (there are no browser cross-origin calls); set it to the frontend origin only if you also poke the API directly from a browser tab.
4. On a free tier that sleeps, the first request can exceed the frontend's 10 second timeout, so the first login attempt can look like a failure. Just retry once it wakes.
